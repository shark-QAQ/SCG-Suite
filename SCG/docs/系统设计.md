## 系统设计：Smart Code Guard（DSH 安全审查插件）

### 1. 设计目标与范围

**一句话定义**：一个以 DSH 插件形态交付的代码安全审查组件，在模型生成或执行代码时提供**主动扫描**与**被动拦截**两层防护，并以可安装 Bundle 的形式分发给团队。

**核心设计原则**（从 DSH 扩展机制推导）：

| 原则       | 含义                                                         | 依据                                           |
| ---------- | ------------------------------------------------------------ | ---------------------------------------------- |
| 关注点分离 | 扫描能力（Tool）与拦截策略（Hook）是两个独立插件模块，可单独启用/禁用 | DSH 微内核将工具注册与策略拦截划分为不同扩展点 |
| 契约优先   | Tool 的 `parameters` 和 `output.schema` 显式声明，`execute` 只返回 canonical 值 | defineTool 强制参数校验与输出规范              |
| 资源自清理 | 所有注册的 tool、listener 必须通过 `ctx.effect()` 或 disposer 管理生命周期 | 热卸载时未清理的资源会造成泄漏                 |
| 隔离验证   | 插件在独立 Profile 中验收，不污染开发环境                    | Profile 提供可复现的测试边界                   |

**明确不做的事**：不修改 DSH 核心代码；不实现完整的 SAST 引擎（用正则 + 规则表覆盖高频风险）；不做跨文件数据流分析（那是重型工具的事，插件聚焦“片段级快速拦截”）。


### 2. 架构分层

```
┌─────────────────────────────────────────────────────────────┐
│                      DSH Runtime                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐ │
│  │  agent-loop │  │  ctx.tools  │  │  Session / Profile  │ │
│  └──────┬──────┘  └──────┬──────┘  └─────────────────────┘ │
│         │                │                                   │
│  ┌──────▼────────────────▼───────────────────────────────┐  │
│  │           Smart Code Guard 插件（本系统）              │  │
│  │  ┌──────────────────┐  ┌──────────────────────────┐   │  │
│  │  │  Tool 模块        │  │  Hook 模块                │   │  │
│  │  │  scan_code_       │  │  监听 tools/pre-execute  │   │  │
│  │  │  security         │  │  拦截高危命令/敏感操作     │   │  │
│  │  └────────┬─────────┘  └────────────┬─────────────┘   │  │
│  │           │                          │                  │  │
│  │  ┌────────▼──────────────────────────▼───────────────┐  │  │
│  │  │              规则引擎（共享）                      │  │  │
│  │  │  regex 规则集 + 语言分类 + 严重级别判定            │  │  │
│  │  └──────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

**模块职责**：

- **Tool 模块**：注册 `scan_code_security` 工具，模型可主动调用对代码片段做安全扫描。返回结构化结果（`safe: boolean`、`issues: Issue[]`），供模型决定是否修正。
- **Hook 模块**：通过 `ctx.on('tools/pre-execute', ...)` 监听工具执行前事件。当检测到模型即将执行高危操作（如 `bash` 工具携带 `rm -rf /`）时，返回 `{ kind: 'deny', reason: '...' }` 阻断执行。
- **规则引擎**：两模块共用同一套规则定义，避免策略分裂。规则以数据形式声明（类型、正则、严重级别、修复建议），便于后续扩展而不改代码。


### 3. 关键接口设计

#### 3.1 Tool 契约（`scan_code_security`）

```typescript
// 输入参数
{
  code: string;        // required, 待扫描代码
  language?: string;   // 可选，用于选择语言特定规则（python/bash/sql/js）
}

// 输出 canonical 值
{
  safe: boolean;
  issues: Array<{
    severity: 'high' | 'medium' | 'low';
    ruleId: string;        // 如 'hardcoded-secret'
    message: string;       // 人类可读描述
    line?: number;         // 行号（若可定位）
  }>;
  summary: string;         // 一句话结论，供 output.render 使用
}
```

`execute` 契约约束：只返回上述对象，不返回内容块；基础设施故障（如正则编译失败）直接 throw；遵守 `exec.signal` 取消。

#### 3.2 Hook 决策契约（`tools/pre-execute`）

```typescript
ctx.on('tools/pre-execute', async (exec, next): Promise<PreToolDecision> => {
  // 1. 只关注特定工具（bash / execute_command / write_file）
  if (!['bash', 'execute_command', 'write_file'].includes(exec.name)) {
    return next();
  }
  // 2. 对 bash 命令做高危检测
  const command = exec.arguments?.command ?? '';
  if (isDangerousCommand(command)) {
    return { kind: 'deny', reason: `安全策略阻止：${command}` };
  }
  // 3. 不满足阻断条件，放行
  return next();
});
```

这里使用 `deny` 而非 `ask`，因为企业场景下高危命令不应给模型“再试一次”的机会。如果需要人工审批，后续可升级为 `ask` 配合 `ctx.approval`。

#### 3.3 规则定义格式

规则以独立 TypeScript 文件维护，插件启动时加载：

```typescript
interface SecurityRule {
  id: string;
  severity: 'high' | 'medium' | 'low';
  languages: string[];        // ['*'] 表示全部
  pattern: RegExp;
  message: string;
  suggestion: string;         // 修复建议，返回给模型
}
```

初始规则集（MVP 覆盖三类高频风险）：
- `hardcoded-secret`：`(password|secret|api_key|token)\s*=\s*['"][^'"]+['"]`，high
- `dangerous-command`：`rm\s+-rf\s+/|mkfs|dd\s+if=`，high（仅 bash）
- `sql-injection`：`(SELECT|INSERT|UPDATE|DELETE).*\+.*(WHERE|VALUES)`，medium


### 4. 数据流

**场景 A：模型主动扫描**

```
模型生成代码 → 模型调用 scan_code_security(code, lang)
  → parameters 校验（DSH 框架层）
  → execute() 执行规则匹配
  → 返回 canonical 值
  → output.render 转为文本给模型
  → 模型根据 issues 决定修正
```

**场景 B：模型试图执行高危操作**

```
模型调用 bash(command: "rm -rf /")
  → tools/pre-execute 触发
  → Hook 插件检测到危险命令
  → 返回 { kind: 'deny', reason: '...' }
  → DSH 框架阻止执行，错误结果返回给模型
  → 模型看到拒绝原因，尝试其他方式
```

**场景 C：正常工具调用（未被拦截）**

```
模型调用 bash(command: "npm test")
  → tools/pre-execute 中 Hook 检测通过
  → next() 放行
  → 正常执行
```


### 5. 工程结构

```
smart-code-guard/
├── package.json              # 声明 dsh.bundle.patch，指向 cordis.patch.yml
├── tsconfig.json
├── cordis.patch.yml          # bundle 配置层：insert 插件行
├── src/
│   ├── index.ts              # 插件入口：export name、inject、apply
│   ├── rules/
│   │   ├── index.ts          # 规则加载与导出
│   │   ├── hardcoded-secret.ts
│   │   ├── dangerous-command.ts
│   │   └── sql-injection.ts
│   ├── scanner.ts            # scan_code_security 的 execute 逻辑
│   └── hook.ts               # tools/pre-execute 监听逻辑
├── dist/                     # tsc 输出（构建产物）
└── verify/
    └── acceptance.md         # 验收步骤与预期输出
```

**配置项**（通过 `cordis.patch.yml` 的 `config` 传入）：

| 配置键        | 类型     | 默认值 | 说明                         |
| ------------- | -------- | ------ | ---------------------------- |
| `enabled`     | boolean  | `true` | 插件总开关                   |
| `blockOnHigh` | boolean  | `true` | Hook 是否拦截 high 级别操作  |
| `extraRules`  | string[] | `[]`   | 额外规则文件路径（绝对路径） |


### 6. 部署与验收设计

**打包**：`npm run build` → `npm pack` 产出 `.tgz`。

**安装到独立 Profile**：
```bash
dsh plugin --profile scg-test add ./dsh-smart-code-guard-0.1.0.tgz
```

### 7. 风险与边界

| 风险                       | 影响               | 缓解                                                      |
| -------------------------- | ------------------ | --------------------------------------------------------- |
| 正则误报                   | 模型被无意义地打断 | 规则分级：high 才触发 deny，medium/low 仅出现在扫描结果中 |
| DSH 版本升级破坏 Hook 签名 | 插件失效           | 锁定 `@deepseek-ai/cordis` 与 DSH 版本，CI 中做冒烟测试   |
| 模型绕过 Hook（换工具名）  | 拦截失效           | 维护“受监控工具名单”，定期根据 DSH 内置工具列表更新       |
| 多行代码跨行匹配困难       | 漏报               | MVP 接受单行匹配，后续可引入简单状态机处理多行            |
